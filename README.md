# My Store — مونورپو

یک سیستم مدیریت فروشگاه کوچک (نقطه‌فروش + انبار + حسابداری دوبل + اسکنر بارکد)
به‌صورت یک **مونورپوی pnpm + turbo**.

- **وب‌اپ:** Next.js 16 (App Router) + React 19 + NextAuth v5 + Tailwind 4
- **دیتابیس:** **MongoDB** با درایور رسمی `mongodb` (بدون ORM، بدون مرحله‌ی generate)
- **موبایل:** Expo SDK 57 + Expo Router — وصل به همان API وب‌اپ (ورود با توکن Bearer)
- **رابط کاربری:** فارسی و راست‌به‌چپ

> **می‌خواهی MongoDB را یاد بگیری؟**
> [`docs/MONGODB-BE-ZABAN-SADE.md`](docs/MONGODB-BE-ZABAN-SADE.md) — توضیح کامل و ساده،
> همراه با نگارش در این پروژه و مقایسه‌ی SQL ↔ MongoDB.

## اجرای سریع (۲ دستور)

```bash
pnpm install
pnpm dev           # وب‌اپ روی http://localhost:3000
```

`pnpm dev` همه‌ی کارها را خودش انجام می‌دهد:

1. اگر `.env.local` نباشد می‌سازد و برای `AUTH_SECRET` یک مقدار تصادفی می‌گذارد.
2. اگر MongoDB در دسترس نباشد، **دیتابیس توسعه‌ی داخل ریپو** (حافظه‌ای) را خودش بالا می‌آورد
   و با خاموش‌شدن، آن را هم می‌بندد.
3. داده‌ی نمونه را می‌ریزد (اگر دیتابیس خالی باشد).
4. `next dev` را روی `0.0.0.0:3000` اجرا می‌کند (برای دسترسی از موبایل/پیش‌نمایش).

> اگر `pnpm: command not found` می‌گیرید: `corepack enable && corepack prepare pnpm@9.0.0 --activate`

اگر ترجیح می‌دهید دیتابیس جدا اجرا شود، همان روش قبلی هم کار می‌کند:

```bash
pnpm db:sandbox    # ترمینال ۱ — دیتابیس روی 127.0.0.1:27017 (داده در حافظه)
pnpm dev           # ترمینال ۲ — وب‌اپ (می‌بیند دیتابیس بالاست و دست به آن نمی‌زند)
```

**بررسی سلامت:** <http://localhost:3000/api/health> — می‌گوید وب‌اپ و دیتابیس سالم‌اند یا نه.

**حساب‌های نمونه:**

| ایمیل | رمز | نقش |
|---|---|---|
| `owner@mystore.ir` | `123456` | OWNER — دسترسی کامل |
| `cashier@mystore.ir` | `123456` | CASHIER — فقط صندوق |

بارکدهای نمونه (برای تست `/scan`): `6281111000019` شیر کم‌چرب · `6281111000026` آب معدنی ·
`6281111000033` نوشابه · `6281111000040` برنج · `6281111000057` چای · `6281111000064` شکر ·
`6281111000071` بیسکوییت · `6281111000088` روغن

## اپ موبایل (Expo)

اپ موبایل **به همان API وب‌اپ وصل است** (دیتابیس و منطق کسب‌وکار جدا ندارد).
کد آن در `apps/mobile/src` است (Expo Router).

### اجرا

```bash
pnpm dev          # ترمینال ۱ — وب‌اپ/API روی :3000 (دیتابیس و seed هم خودش)
pnpm dev:mobile   # ترمینال ۲ — اپ موبایل روی http://localhost:8081
```

> `pnpm dev` با turbo هم وب‌اپ و هم موبایل را بالا می‌آورد؛ اگر فقط موبایل را
> می‌خواهید، `pnpm dev:mobile` را کنار `pnpm dev:web` اجرا کنید.

`pnpm dev:mobile` دو چیز را اجرا می‌کند:

1. **Metro** روی پورت `8082` (باندل React Native/وب)
2. یک **پروکسی** روی پورت `8081` که `/api/**` را به وب‌اپ (`:3000`) می‌برد و
   بقیه را به Metro. چون درخواست‌ها هم‌ریشه (same-origin) می‌شوند، نه CORS
   مشکل می‌شود و نه نیاز است آدرس `localhost` را داخل کد بنویسیم.

### ورود

صفحه‌ی ورود را باز کنید (<http://localhost:8081/login>) و همان حساب‌های نمونه را
بزنید: `owner@mystore.ir` / `123456`.

تفاوتش با وب: وب با **کوکی نشست** Auth.js کار می‌کند، ولی React Native کوکی
نگه نمی‌دارد. پس موبایل `POST /api/auth/mobile/login` را صدا می‌زند و یک
**توکن Bearer** می‌گیرد (۳۰ روز اعتبار) که در AsyncStorage ذخیره می‌شود و در هر
درخواست با هدر `Authorization: Bearer <token>` می‌رود. توکن با همان
`AUTH_SECRET` و همان کتابخانه‌ی Auth.js ساخته/خوانده می‌شود (با salt جدا از
کوکی نشست وب)، و `requireStoreUser()` در API هر دو راه را قبول می‌کند.

### صفحه‌ها

| تب | محتوا |
|---|---|
| `امروز` | خلاصه‌ی مالی (فروش/هزینه/سود/ارزش انبار/کم‌موجودی) از `/api/reports/summary` |
| `فاکتورها` | لیست فاکتورها با فیلتر وضعیت از `/api/invoices` |
| `اسکن` | جست‌وجوی بارکد + ثبت رویداد اسکن (فروش/شمارش/ورود/خروج/اصلاح) + فید آخرین اسکن‌ها |
| `پروفایل` | کاربر جاری، نقش، وضعیت سرور/دیتابیس (`/api/health`) و خروج |

### روی گوشی واقعی

اپ باید بتواند به سرور برسد، پس آدرس API را بدهید (آی‌پی ماشین شما در همان
شبکه‌ی وای‌فای):

```bash
EXPO_PUBLIC_API_URL=http://192.168.1.10:3000 pnpm dev:mobile
# بعد با Expo Go یا build توسعه، همان آدرس را اسکن/وارد کنید
```

در حالت وب این متغیر لازم نیست (خالی = همان origin، یعنی همان پروکسی `:8081`).

## انتخاب دیتابیس

سه حالت پشتیبانی می‌شود؛ کد برنامه برای همه‌ی آن‌ها **یکی** است.

### ۱) سرور توسعه‌ی داخل ریپو (پیش‌فرض)

```bash
pnpm db:sandbox
```

`tooling/dev-db` یک سرور سازگار با پروتکل MongoDB بالا می‌آورد
(`@rckflr/easydb-server` با adapter حافظه). هیچ نصب اضافه‌ای لازم نیست.

محدودیت‌هایش (که در کد لحاظ شده‌اند): تراکنش پشتیبانی نمی‌شود →
`runInTransaction()` به نوشتن متوالی برمی‌گردد؛ ایندکس `unique` enforce نمی‌شود →
یکتایی بارکد در کد چک می‌شود؛ `$facet` کار نمی‌کند → در `stats.ts` استفاده نشده.
داده‌ی آن در حافظه است و با خاموش‌شدن پاک می‌شود.

### ۲) Docker (MongoDB واقعی، با تراکنش)

```bash
pnpm docker:up
pnpm db:seed
pnpm dev
```

`mongo:7` به‌صورت **replica set تک‌گره** بالا می‌آید (چون MongoDB فقط روی replica set
از تراکنش چندداکیومنتی پشتیبانی می‌کند)، به‌همراه:

- رابط گرافیکی mongo-express روی <http://localhost:8081>
- Redis روی `6379` (اختیاری؛ برای صف رویدادهای Realtime)

### ۳) MongoDB Atlas (ابری، برای استقرار)

یک کلاستر رایگان M0 بساز، IP خودت را whitelist کن و `MONGODB_URI` را تنظیم کن.

## ساختار مونورپو

```
apps/
  web/            # Next.js 16 — وب‌اپ اصلی (صفحه‌ها + API routes)
  mobile/src/     # Expo Router — اپ موبایل (ریشه‌ی اپ همان src است)
packages/
  shared-types/   # تایپ‌های مشترک (DTOها، نقش‌ها، وضعیت فاکتور، …)
  shared-utils/   # توابع کمکی (formatMoney، slugify، …)
  ui-kit/         # کامپوننت‌های UI (Button, Card, Input, Badge)
  api-client/     # کلاینت تایپ‌دارِ API برای موبایل/کلاینت‌های دیگر
tooling/
  dev-db/         # سرور MongoDB-سازگار برای توسعه
docs/
```

### لایه‌ی داده (همه در `apps/web/src/lib/`)

| فایل | مسئولیت |
|---|---|
| `db.ts` | اتصال، هلپرهای `oid()`، ساخت ایندکس‌ها، `runInTransaction()` |
| `models.ts` | شکل سند‌ها در TypeScript |
| `repositories.ts` | خواندن/نوشتن + وصل‌کردن روابط بین سند‌ها |
| `serialize.ts` | تبدیل سند خام → DTO تمیز |
| `stats.ts` | همه‌ی aggregateها و ریاضی گزارش‌ها (API و صفحه‌ها از همین استفاده می‌کنند) |
| `ledger.ts` | سند‌های حسابداری بدهکار/بستانکار |
| `invoice-service.ts` | صدور فاکتور، پرداخت، لغو، اثر روی موجودی و بدهی مشتری |
| `scan-service.ts` | پردازش رویداد اسکن بارکد |
| `auth.ts` | NextAuth با provider اعتبارنامه‌ای و نقش‌ها |

### صفحه‌ها

| مسیر | محتوا |
|---|---|
| `/` | صفحه‌ی ورودی |
| `/login` · `/register` | ورود و ثبت‌نام فروشگاه جدید |
| `/dashboard` | آمار امروز/ماه، ارزش انبار، کم‌موجودی‌ها |
| `/products` | CRUD محصولات و دسته‌بندی‌ها |
| `/customers` | CRUD مشتریان و مانده‌حساب |
| `/accounting` | لیست فاکتورها + ساخت فاکتور |
| `/accounting/invoices/[id]` | جزئیات فاکتور، ثبت پرداخت، تغییر وضعیت/لغو |
| `/accounting/expenses` | هزینه‌ها و دسته‌بندی هزینه |
| `/accounting/reports` | سود و زیان، گردش حساب، گزارش فروش |
| `/scan` | اسکنر بارکد (دوربین) + ورود/خروج کالا و فید زنده |

### API

`GET/POST/PATCH/DELETE` روی:
`/api/products`، `/api/products/[id]`، `/api/products/lookup`، `/api/categories`،
`/api/customers`، `/api/invoices`، `/api/invoices/[id]`، `/api/invoices/[id]/payments`،
`/api/expenses`، `/api/expense-categories`، `/api/scan`، `/api/scan/stream` (SSE)،
`/api/reports/{summary,profit-loss,sales}`، `/api/auth/register`،
`/api/auth/mobile/login` (توکن Bearer برای اپ موبایل)، `/api/auth/mobile/session`،
`/api/health`.

**قراردادها:**

- پاسخ موفق = خودِ DTO (یا یک `Page` با `items` و `total` و `page` و `pageSize`)؛
  پاسخ خطا = `{ "error": "پیام فارسی" }`.
- `id`ها در JSON **رشته‌ی هگز ۲۴ کاراکتری** هستند (نه `ObjectId`).
- **چندفروشگاهی:** هر کوئری با `storeId` محدود می‌شود؛ نقش‌ها `OWNER` / `ACCOUNTANT` / `CASHIER`.
- خطاهای اعتبارسنجی `400`، تداخل یکتایی `409`، بدون نشست `401`، بدون دسترسی `403`.
- ورودی‌ها با **zod** اعتبارسنجی می‌شوند.
- **دو راه احراز هویت:** کوکی نشست Auth.js (وب) یا هدر
  `Authorization: Bearer <token>` (موبایل). هر دو در `requireStoreUser()`
  بررسی می‌شوند، پس routeها نیازی به تغییر ندارند.

## منطق کسب‌وکار

- **صدور فاکتور:** کاهش موجودی، ثبت حرکت انبار، ثبت سند حسابداری
  (بدهکار صندوق + بدهکار حساب دریافتنی / بستانکار درآمد فروش / بدهکار بهای تمام‌شده + بستانکار انبار)،
  به‌روزرسانی مانده‌حساب مشتری.
- **پرداخت جزئی** → وضعیت `PARTIAL` و مانده‌ی بدهی؛ **تسویه** → `PAID`.
- **لغو فاکتور** → بازگشت موجودی، برگشت سند حسابداری، صفرشدن اثر روی مانده‌حساب مشتری.
- **اسکن بارکد:** `SALE` / `COUNT` / `CHECK_IN` (ورود کالا، افزایش موجودی) /
  `CHECK_OUT` (خروج، کاهش) / `ADJUSTMENT`.
  بارکد ناشناخته هم ذخیره می‌شود (با `productId: null`) تا بعداً به محصول وصل شود.
- **دفتر کل** همیشه باید متوازن باشد: مجموع بدهکار == مجموع بستانکار.

## عیب‌یابی (پر تکرارترین‌ها)

### «سرور اصلاً بالا نمی‌آید»
- **`pnpm: command not found`** →
  `corepack enable && corepack prepare pnpm@9.0.0 --activate` (یا `npm i -g pnpm@9`).
- **`Another next dev server is already running`** → یک سرور dev دیگر برای همین پوشه
  بالاست. خط پایان پیام می‌گوید `kill <PID>`؛ یا همان آدرس را در مرورگر باز کنید.
  (Next.js 16 برای هر پوشه فقط یک dev server اجازه می‌دهد.)
- **پورت ۳۰۰۰ گرفتار است** → اگر `PORT` را خودتان تعیین نکرده باشید، Next خودش
  پورت آزاد بعدی (۳۰۰۱) را می‌گیرد؛ در ترمینال همان «Local:» را باز کنید.

### «ورود کار نمی‌کند / بعد از ورود دوباره به /login برمی‌گردم»
- **`AUTH_SECRET` تنظیم نشده باشد، همین اتفاق می‌افتد**: Proxy (که نشست را می‌خواند)
  نمی‌تواند JWT را باز کند. `pnpm dev` اگر `.env.local` نباشد خودش می‌سازد و راز
  تصادفی می‌گذارد؛ اگر فایل را دستی ساخته‌اید، مقدارش را پر کنید
  (`openssl rand -base64 32`).
- **پیام «ایمیل یا رمز عبور اشتباه است» با رمز درست** → معمولاً دیتابیس بالا نیست.
  صفحه‌ی ورود خودش وضعیت دیتابیس را چک می‌کند و هشدار می‌دهد؛ خروجی
  <http://localhost:3000/api/health> را هم ببینید. راه‌حل: `pnpm dev` (خودکار) یا
  `pnpm db:sandbox`.
- در لاگ سرور دنبال این‌ها بگردید: `MissingSecret` (راز ناقص) ·
  `MongoServerSelectionError` / `ECONNREFUSED` (دیتابیس بالا نیست).

### «داده‌ها بعد از ری‌استارت پاک می‌شوند»
دیتابیس پیش‌فرض توسعه (`pnpm db:sandbox`) **در حافظه** است. برای داده‌ی پایدار
از Docker (`pnpm docker:up`) یا MongoDB Atlas استفاده کنید. برای ریختن دوباره‌ی
داده‌ی نمونه: `pnpm db:reset`.

### «خطاهای عجیبِ بیلد/کش»
`.next` را پاک کنید: `rm -rf apps/web/.next` و بعد `pnpm dev`.

## نکات توسعه

- Next.js 16 تفاوت‌هایی با نسخه‌های قبلی دارد. اگر شک کردی، مستندات داخل
  `node_modules/next/dist/docs/` را بخوان.
- `packages/*` به‌صورت **سورس TypeScript** مصرف می‌شوند (با `transpilePackages`)؛
  نیازی به بیلد جدا ندارند.
- فایل `.env.local` در گیت نادیده گرفته می‌شود؛ فقط `.env.example` ثبت می‌شود.
- برای ریست کامل داده‌ی توسعه: `pnpm db:reset`.
